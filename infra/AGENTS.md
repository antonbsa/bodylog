# infra

Conventions for `infra/` (D1 migrations, local-db scripts, the shared `errors.ts`).

## Migrations

- Migrations are hand-written SQL in `infra/migrations/`, named `<YYYYMMDDHHMMSS>_<snake_case_name>.sql` with a UTC timestamp from `date -u +%Y%m%d%H%M%S` (ADR 0045). `0001`, `0002` and `0003` are the legacy index-prefixed files and keep their names. Every wrangler environment reads them through `migrations_dir` in `apps/api/wrangler.toml`.
- Symptom: two branches add migrations that apply in an order their authors didn't expect, or a migration merged to `main` has to be renamed. Why it slips: wrangler applies files in lexicographic order and tracks them by filename, and git sees no conflict between differently named files. Verify: after merging `main` into a branch with an unmerged migration, compare its timestamp with the newest one in `ls infra/migrations` on `main`; when it is older, rename it to a fresh `date -u +%Y%m%d%H%M%S` before merging the PR. A migration already on `main` never changes name.
- Apply locally with `npm run db:migrate:local` (or `npm run db:setup:local`, which also seeds an empty table). Remote databases get migrations only from the deploy workflows: preview on every merge to `main`, production when a release is published (ADR 0041). A migration therefore runs against preview's data before production's, without a manual step.
- Symptom: a renamed, re-stamped or edited migration never runs on a database that already applied it, or `db:migrate:local` fails with `duplicate column name`. Why it slips: wrangler tracks applied migrations by filename in the `d1_migrations` table, not by content, so local D1 sees a new filename as unapplied, and `tests/api/migrations.test.ts` replays the files on a fresh in-memory SQLite. Verify: a schema change is always a new file, never an edit to an applied one; extend `migrations.test.ts` for it and run `npm run db:migrate:local`, which applies only the new file; after a re-stamp, `npm run db:query:local -- "SELECT name FROM d1_migrations"` still lists the old filename. Repair: when the SQL is unchanged, repoint the row with `npm run db:query:local -- "UPDATE d1_migrations SET name = '<new>.sql' WHERE name = '<old>.sql'"`, otherwise delete `apps/api/.wrangler/state` and re-run `npm run db:migrate:local`; both mutate local D1 and need the owner's yes first.
- A schema change also updates the repository in `apps/api/src/db/repositories/` and [docs/reference/database.md](../docs/reference/database.md) in the same change. `tests/api/database-doc.test.ts` fails when the page's diagram and the migrated columns or their PK/FK/UK markers disagree; it doesn't read the prose. Symptom: the Tables, Unique Keys or Lifecycles sections describe a table, key or enumeration value the schema no longer has, or miss a new one. Why it slips: the test compares only the diagram, and the API tests read the SQL, never the prose. Verify: for each table, unique key or enumeration value the migration adds or removes, `grep -n "<name>" docs/reference/database.md` finds it as it now is in those sections.

## Local DB scripts

- `infra/scripts/local-db/` (commands in its [README](scripts/local-db/README.md)) only ever uses wrangler's `--local` mode; keep every new command local-only.
- `npm run db:reset:local` deletes every local measurement before reseeding, and deleting `apps/api/.wrangler/state` wipes the whole local D1. Both need the owner's yes first; `guard-bash.mjs` asks before any `rm` of `.wrangler` state.
- Seed dates are generated relative to today in TypeScript because weekly grouping depends on the current date; pass `-- --today YYYY-MM-DD` for deterministic data.
